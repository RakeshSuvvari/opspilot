# OpsPilot final benchmark results

These are the measured results used in the project README. They were produced locally on September 10, 2026 with `gpt-5.4-mini` using the Phase 10 controlled Kubernetes benchmark suite.

## Benchmark methodology

OpsPilot is evaluated with deterministic benchmark cases rather than a second LLM acting as a judge. Each benchmark case defines:

- the expected incident status;
- one or more acceptable root-cause signal groups;
- the Kubernetes and/or GitHub tools expected to be used;
- expected affected-resource signals;
- whether RAG usage is expected;
- a minimum number of timeline events;
- optional deployment/source-change signals; and
- a pass threshold.

For each run, OpsPilot performs a live investigation against a controlled local Kubernetes `kind` cluster. The generated structured `IncidentReport` is scored against the case definition.

Unless otherwise specified, a run **passes when its deterministic evaluation score is at least 80/100**.

The benchmark also records latency, tool usage, token usage, and estimated model cost directly from the completed investigation.

The ten scenarios cover missing configuration, OOMKilled, broken readiness, downstream timeout, image pull failure, missing Secret, bad downstream DNS/configuration, broken liveness, application/probe port mismatch, and a healthy control.

### What each metric means

#### Runs

**Definition:** Total number of completed benchmark investigations.

**Calculation:**

```text
Runs = number of scenarios × repeats
     = 10 × 3
     = 30
```

Repeating each scenario reduces the chance that the final result reflects only one stochastic LLM response.

#### Pass rate

**Definition:** Percentage of benchmark runs whose deterministic evaluation score meets or exceeds the case pass threshold.

For the primary suite, the threshold is **80/100**.

**Calculation:**

```text
Pass rate = passed runs / total runs × 100
          = 25 / 30 × 100
          = 83.33%
```

A run can fail even when parts of its diagnosis are correct if the combined evaluation score falls below 80.

Pass rate should therefore be interpreted as **overall benchmark success**, not as root-cause accuracy alone.

#### Root-cause accuracy

**Definition:** Average coverage of the root-cause signals expected for each benchmark case.

Each case contains one or more **signal groups**. A group is considered matched when the generated `root_cause` contains at least one acceptable phrase from that group.

For one run:

```text
Root-cause coverage =
    matched root-cause signal groups
    -------------------------------- × 100
    total root-cause signal groups
```

The benchmark result is the arithmetic mean of this percentage across all runs.

```text
Primary benchmark root-cause accuracy = 91.11%
```

This is a deterministic signal-coverage metric. It does **not** mean that an LLM judge assigned a 91.11% semantic correctness score.

#### Status accuracy

**Definition:** Percentage of runs where the report's top-level incident status exactly matches the expected status in the evaluation case.

For each run:

```text
status_correct =
    1 if report.status == expected_status
    0 otherwise
```

Across the benchmark:

```text
Status accuracy =
    correct status predictions / total runs × 100
```

The primary benchmark produced **76.67% status accuracy**.

Status accuracy is intentionally separate from pass rate. A run can still score at least 80/100 after a status mismatch if it performs strongly on root-cause evidence, tool usage, affected resources, confidence, RAG expectations, and timeline quality.

#### Required-tool coverage

**Definition:** Measures whether OpsPilot used the live diagnostic tools that the benchmark case expected for a proper investigation.

For each run:

```text
Tool coverage =
    number of required tools actually used
    --------------------------------------- × 100
    number of required tools
```

The final metric is the mean tool coverage across all runs.

The primary benchmark achieved **96.67% required-tool coverage**.

For GitHub change-intelligence cases, the required GitHub change tools are also included when calculating this coverage.

This metric measures **investigation coverage**, not whether every tool call returned useful evidence.

#### Remediation recommendation coverage

**Definition:** Measures whether the final remediation recommendations contain the expected corrective-action signals for the scenario.

Each scenario defines acceptable remediation signal groups. The benchmark joins the report's remediation recommendations into one text value and checks whether at least one acceptable signal from each group is present.

For a run:

```text
Remediation coverage =
    matched remediation signal groups
    ---------------------------------- × 100
    total remediation signal groups
```

The result is averaged across benchmark runs.

The primary benchmark achieved **100.00% remediation recommendation coverage**.

This metric evaluates the **recommendation**, not whether a human approved the action or whether a write operation was executed successfully. Actual HITL execution is tested separately by the remediation workflow.

For scenarios that intentionally define no remediation signal groups, coverage is treated as 100%.

#### Average evaluation score

**Definition:** Mean deterministic case score across all benchmark runs.

For normal Kubernetes/RAG benchmark cases, each report can receive up to 100 points:

| Evaluation component | Maximum points |
|---|---:|
| Expected status | 15 |
| Root-cause signals | 40 |
| Required tools | 20 |
| Expected affected resource | 10 |
| Confidence | 5 |
| Expected RAG behavior | 5 |
| Minimum timeline evidence | 5 |
| **Total** | **100** |

The root-cause and tool portions receive proportional partial credit.

For example, if a case requires four root-cause signal groups and three are matched:

```text
Root-cause score = 40 × 3/4 = 30 points
```

Confidence is scored as:

```text
HIGH   = 5 points
MEDIUM = 2.5 points
LOW    = 0 points
```

A run passes when:

```text
evaluation score >= case pass threshold
```

The primary suite uses an 80/100 threshold and achieved an **average evaluation score of 88.36/100**.

The average score is useful for distinguishing two benchmarks with similar pass rates: one may barely pass most cases while another may consistently score near 100.

#### Median investigation latency

**Definition:** Middle end-to-end investigation duration after all run latencies are sorted.

The duration comes from the investigation's recorded `elapsed_ms` metric and includes the agent investigation and tool interaction represented by that run.

For 30 runs, the median is the midpoint of the two central observations.

```text
Median latency = 8.481 seconds
```

Median is reported because it is less sensitive to occasional slow model/tool executions than the arithmetic mean.

#### P95 investigation latency

**Definition:** A tail-latency measure showing the investigation duration at or below which approximately 95% of benchmark runs completed.

OpsPilot uses the **nearest-rank percentile** calculation:

```text
rank = ceil(0.95 × number of runs)
P95  = latency at that rank after sorting
```

For the 30-run benchmark:

```text
rank = ceil(0.95 × 30)
     = 29
```

Therefore the 29th sorted latency is reported as P95:

```text
P95 latency = 12.934 seconds
```

This metric helps expose slower investigations that the median alone can hide.

#### Average tool calls

**Definition:** Mean number of MCP/function-tool calls made per investigation.

```text
Average tool calls =
    sum of tool calls across runs
    -----------------------------
    total runs
```

The primary benchmark averaged **5.03 tool calls per investigation**.

This counts total calls, not only unique tool names.

#### Total tokens

**Definition:** Sum of input and output model tokens consumed by all benchmark runs.

```text
Total tokens =
    total input tokens + total output tokens
```

Across the 30-run benchmark:

```text
Total tokens = 469,576
```

This is useful for understanding the inference footprint of the complete evaluation and for estimating model cost.

#### Estimated text-token cost

**Definition:** Estimated model inference cost calculated from measured input/output tokens and the benchmark's configured per-million-token rates.

**Calculation:**

```text
Estimated cost =
    (input tokens  / 1,000,000 × input price per million)
  + (output tokens / 1,000,000 × output price per million)
```

For the 30-run benchmark, the resulting estimate was:

```text
$0.4365
```

This is an **estimated text-token cost**, not a complete infrastructure bill. It does not include PostgreSQL, Kubernetes compute, embedding ingestion, network costs, tool-service compute, or cached-input pricing adjustments.

### Change-correlation metric

**Definition:** Measures whether OpsPilot both used the expected GitHub change-intelligence tools and returned the expected deployment/source-change evidence.

For each GitHub-enabled case, two quantities are calculated:

1. **Change-content coverage** — percentage of expected change signal groups found in the structured `change_correlation` output.
2. **Change-tool coverage** — percentage of required GitHub change tools actually used.

The per-run metric is:

```text
Change correlation =
    (change-content coverage + change-tool coverage) / 2
```

The reported benchmark value is the arithmetic mean across GitHub change-intelligence runs.

```text
Change correlation = 87.50%
```

This means the metric evaluates both **what OpsPilot concluded about the deployment change** and **whether it collected the expected source-change evidence**.

### Change-aware evaluation score

GitHub-aware evaluation cases still total 100 points, but the scoring weights are adjusted to make room for explicit source-change validation:

| Evaluation component | Maximum points |
|---|---:|
| Expected status | 15 |
| Root-cause signals | 30 |
| Required base tools | 15 |
| Expected affected resource | 10 |
| Confidence | 5 |
| Expected RAG behavior | 5 |
| Minimum timeline evidence | 5 |
| GitHub change correlation | 15 |
| **Total** | **100** |

The 15 change-correlation points consist of:

```text
5 points  -> structured change-correlation result is present
5 points  -> expected change-content signals are covered
5 points  -> required GitHub change tools are used
```

The remaining GitHub benchmark metrics use the same definitions described for the primary benchmark.

Because this suite contains only four cases, its results should be treated as a focused validation of deployment/source correlation rather than a broad statistical estimate.

## RAG ablation — descriptive single-run comparison

| Metric | RAG on | RAG off |
|---|---:|---:|
| Runs | 10 | 10 |
| Pass rate | 70.00% | 90.00% |
| Root-cause accuracy | 83.33% | 93.33% |
| Status accuracy | 80.00% | 50.00% |
| Required-tool coverage | 95.00% | 97.50% |
| Average score | 85.33 | 84.33 |
| Median latency | 9.831 s | 8.589 s |
| Total tokens | 173,196 | 142,417 |
| Estimated text-token cost | $0.1580 | $0.1331 |

The RAG ablation uses the same metric definitions and deterministic evaluation framework as the primary benchmark. The only intended experimental difference is whether the `search_knowledge` RAG capability is enabled.

Because this ablation used **one stochastic model run per scenario**, it is descriptive only and does not support a claim that RAG universally improves or degrades accuracy.

In this sample:

- RAG-on produced higher status accuracy: 80.00% vs. 50.00%.
- RAG-on produced a slightly higher average evaluation score: 85.33 vs. 84.33.
- RAG-off produced a higher pass rate and root-cause signal accuracy in this particular single-run sample.
- RAG-on required more tokens and had higher median latency.

The mixed result is why the project does **not** claim that RAG universally improves benchmark accuracy. Its architectural purpose is to provide operational/runbook context while live Kubernetes evidence remains authoritative.

## How the major metrics relate

The metrics intentionally measure different properties, so their percentages should not be expected to match.

For example:

```text
Pass rate
    ↓
Did the complete weighted report score >= 80?

Root-cause accuracy
    ↓
How many expected RCA signal groups were identified?

Status accuracy
    ↓
Was the top-level incident/healthy classification correct?

Required-tool coverage
    ↓
Did the investigation collect the expected evidence sources?

Remediation coverage
    ↓
Did the recommendation contain the expected corrective action?

Change correlation
    ↓
Did GitHub-enabled runs collect and explain the expected deployed change?
```

This explains why the primary benchmark can have:

```text
83.33% pass rate
91.11% root-cause accuracy
76.67% status accuracy
96.67% required-tool coverage
100.00% remediation recommendation coverage
```

A report may, for example, misclassify the top-level status but still correctly identify the root cause, inspect the right evidence, identify the affected resource, and recommend the expected remediation. Conversely, a correct status alone is not sufficient to pass.

## Interpretation of the final results

The 30-run primary benchmark supports the following project-level observations:

- OpsPilot identified the expected root-cause signals with **91.11% average coverage**.
- It used **96.67% of expected diagnostic tools**, showing that investigations generally collected the intended live evidence.
- All evaluated remediation signal groups were covered, producing **100.00% remediation recommendation coverage**.
- **25 of 30 runs passed** the complete deterministic evaluation, resulting in an **83.33% pass rate**.
- Median end-to-end investigation latency was **8.481 seconds**, while P95 was **12.934 seconds**.
- The separate GitHub fixture evaluation produced **87.50% change-correlation coverage**.
- The benchmark demonstrates useful performance across controlled failure modes, but it is not intended to represent production incident accuracy across arbitrary Kubernetes environments.

## Evaluation limitations

- The environment is a controlled local Kubernetes `kind` cluster rather than a production multi-cluster deployment.
- The primary result contains 30 runs across 10 scenarios, so it is a project benchmark rather than a large statistical study.
- Failure modes are deliberately injected and known to the deterministic evaluation definitions.
- Root-cause accuracy is signal-group coverage, not a human or LLM semantic-judging percentage.
- Required-tool coverage measures expected evidence collection but does not independently grade the quality of every tool response.
- Remediation recommendation coverage evaluates suggested corrective actions, not end-to-end production recovery success.
- The GitHub benchmark uses deterministic fixture commit/PR histories for four scenarios.
- The RAG ablation contains one run per scenario and should be interpreted descriptively.
- Model outputs remain stochastic; repeated runs can produce different tool sequences, wording, and scores.
- Cost is an estimate from text-token usage only; embedding/tool/infrastructure costs and cached-input discounts are not included.

## Evaluation notes

- The primary benchmark pass threshold is 80/100.
- Evaluation scoring is deterministic; a second LLM is not used as a judge.
- RAG is supporting evidence and cannot substitute for live Kubernetes evidence.
- The benchmark records the model-generated investigation separately from the deterministic scoring logic.
